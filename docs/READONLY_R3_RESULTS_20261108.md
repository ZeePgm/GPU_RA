# R3 请求合并、覆盖扩展与混合选择结果

2026-11-08。**声明的读取适配器实验范围内，功能、机制和对齐连续读取主条件的性能验收通过。** 运行于真实 GPU，使用当前源码重新构建的共享运行时与 HBF 后端。

## 实现与能力边界

- `AsyncDeviceClient::gate_load_adaptive/warp_load_adaptive`：仅当活跃 lane 按 lane 顺序形成连续跨度，且跨度属于同一个注册区间时合并。重复、空洞、逆序、跨注册区间保持标量请求；物理 sector/DLU 边界由后端拆分。
- PTX 增加显式 `uniform_warp_reads` 策略。解析器要求直线控制流、所有全局读先于写、无提前返回；启动必须为完整 warp。统一 helper 收集原 predicate，任一成员失败即阻止整个 warp 进入下一次 collective。
- hybrid 针对已知等价的读取模板先检查 PTX 能力，受限控制流不通过时选择显式 CUDA。没有把未知任意 PTX 静默替换为 CUDA。
- 完整张量按 256 lane 有界批次读取；实际数据写入 GPU 镜像，全部覆盖完成后才交给保持原算术顺序的 CUDA norm/矩阵消费者。完整消费者输出与原始权重计算逐位一致，并另用 CPU 检查算术。

这是完整张量读取适配器及其消费者的实验。模型留出使用真实 GGUF 权重、不同模型/层与 token 批大小；另补充了真实 llama 在 31/32/33 token 上下文产生的 prefill/decode 激活回放。HBF 读取仍在独立适配器中验证，未接入完整 llama 推理流程，未测端到端 TTFT/TPOT，也没有宣称覆盖全模型全部权重。

## 正确性、覆盖和依赖

| 验收 | 结果与依据 |
|---|---|
| 边界访问 | 14 种布局 × 4/16 B × PTX/CUDA × 合并开关，共 112 个 GPU 进程通过；含连续、跨 sector/DLU、尾 warp、稀疏/空 predicate、单 lane、重复、逆序、空洞、stride、相邻注册范围、双 warp、双 CTA |
| 独立覆盖 oracle | Python 将实际父跨度展开成逐字节多重集，与独立 lane 计划精确比较；保留重复读取次数，禁止缺失和拓宽 |
| 等待合同 | 每个活跃 lane 的实际消费时刻不得早于其父请求到达加建模等待；正确性模式 time_scale=100，性能模式关闭设备计时 |
| 失败与排空 | 两路径 × 两开关 × 越界/后端失败，共 8 项拒绝成功；析构后 CUDA 同步成功 |
| 完整张量 | 8 个真实张量、32 次路径运行，独立分母来自 GGUF/profile 形状和字节数；所有字节精确覆盖一次、镜像哈希一致 |
| 层/模型留出 | Qwen3-0.6B 第 10 层为开发集合；SmolLM2 第 0/23 层、Qwen3-1.7B 第 27 层为留出；均包括完整 norm/down，token 批分别 1/3/7 |
| 混合策略额外留出 | SmolLM2 第 29 层 norm/down、5-token 批；正常直线模板选 PTX，等价的带跳转模板选 CUDA，4 次运行全部通过 |
| 真实上下文留出 | 固定 native ubatch=32，选择 31/32/33 token（边界前/边界/边界后）；SmolLM2 第 29 层 norm/down 的末次 prefill 微批和首步 decode，PTX/CUDA 合并路径共 24 次回放全部通过；三个上下文的 decode 激活哈希确实不同 |
| 组件回归 | 28 项 CTest 通过，含原解析器合同及新增策略的 4 个正例、20 个非法控制流/访存顺序变体 |

对齐的 32 lane × 4 B 夹具，父请求从 32 降到 1，合并跨度 128 B、恰好覆盖 2 个 sector。这些计数来自明确访问语义，因此要求完全一致，未使用经验容差。

完整张量共 35,013,120 字节。以 Qwen3-1.7B 的完整 down 矩阵为例：25,165,824 B，双方都以每 lane 16 B 读取；标量为 1,572,864 次请求，合并为 49,152 次，精确减少 32 倍。累计 sector 贡献从 1,572,864 降到 393,216，消除了同一 sector 在相邻标量请求中的重复贡献；唯一字节覆盖保持不变。实际返回数据、GPU 消费输出和依赖逐项通过。

## 性能及判定

主指标是读取适配器启动 API 前至同步返回的墙钟，包含 GPU 读取、mailbox、主机服务、后端和等待。输入准备、验证、模块加载/初始化不计入稳态主指标。不能把该读阶段结果解释为整个模型相同倍数的加速。

先导共 48 个进程：每路径 8 对 A/A，另有每路径 4 对开发 A/B。A/A 最大绝对差 PTX 1.915 ms、CUDA 0.864 ms；开发 A/B 中位节省分别约 10.556/10.575 ms，预定的分辨能力检查通过。

正式阶段每路径主条件 32 对独立进程；另对 stride、单 lane、稀疏和跨 DLU 各做 12 对，总计 160 对/320 进程。每进程预热一次，三次观测取均值；配对顺序平衡并随机化。主终点使用配对差值的中位数，避免沿用此前对异常值敏感的均值推断。区间来自二项分布次序统计，两个主比较共享 0.05 错误预算；样本量和停止规则在正式采样前冻结。

主条件为 256 lane × 4 B，同样读取 1024 B，父请求从 256 降到 8。单位 ms；差值为标量−合并：

| 路径 | 标量耗时中位数 | 合并耗时中位数 | 配对节省中位数 | 调整后区间 |
|---|---:|---:|---:|---|
| ptx | 10.9148 | 0.3296 | 10.5930 | [10.4463, 10.9659] |
| cuda | 11.1194 | 0.3200 | 10.7653 | [10.4396, 11.2010] |

两个主条件的 32 对样本均为正收益，区间下界高于零，支持该条件下存在正的中位耗时节省。这里只对“存在节省”使用零界，没有凭空设定应用最小有意义收益，也没有据此自动切换完整应用默认路径。

不连续 stride 的两路径区间均跨零；单 lane 也未建立稳定收益。稀疏但按活跃 lane 排列连续、跨 DLU 的描述性结果显示较大节省，但它们未作为额外确认性主假设。两种接入技术的优劣仍应按具体调用方式判断；本轮成立的是各自路径内部的合并收益。

## 排查并修复的扩展限制

1. 2048 个并发标量生产者在完整矩阵测试中触发既有 1 秒请求超时。完整张量改为每批 256 lane，覆盖分母不变；全部最终实验重新验证。
2. 大矩阵流式访问触及累计 1000 万事件限制。诊断确认为 `LimitReached: total event limit reached`。按完整标量访问量配置事件预算 `max(10M,128×(bytes/width+ceil(bytes/4096)))`，作为软件资源保护额度，保持数值/覆盖/依赖验收标准不变。
3. AsyncRuntime 保留原始异常文本，LiveTimingService 报告终止原因，避免后续只能看到笼统状态码。

失败批次与诊断日志保留，不进入正式性能统计。最终五个阶段的源码和二进制哈希均复核通过，另存完整快照。

## 上下文留出补充说明

该补充沿用已冻结的合并和混合选择规则。使用原生 llama 在 GPU 上执行实际 token 序列，回调在相关算子完成后采集输入激活；保留全部微批采集记录，验证末次 prefill 微批和首步 decode。31/32/33 来自固定 ubatch=32 的结构边界，不是任意选择长度。权重来自同一 GGUF 清单；R3 回放读取整个张量后，使用采集激活完成完整 GPU 消费者计算，对原始权重参考逐位比较，并执行原有 CPU 检查、覆盖和逐 lane 等待检查。全部 24 次通过，源码和程序哈希在批次结束再次校验。

此阶段不采集性能、不改变已有正式性能样本；其作用是验证真实上下文改变激活后，读取及消费合同仍成立。它不验证完整模型内多算子同时接入或与 KV 的资源竞争，那属于后续模型集成/联合验收。
