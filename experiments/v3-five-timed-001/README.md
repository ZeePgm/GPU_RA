# 五类权重的原生读取与在线介质等待

在 Qwen3-0.6B F16、44 输入和两个输出 token、原生 F16 KV 条件下，将 FFN 归一化、Q、FFN 下投影、词嵌入和输出投影作为五个显存地址范围一次登记。预填充和解码共用一次登记。CUDA 编译处理范围是原生 `binbcast.cu`、`convert.cu`、`getrows.cu` 和 `mmvf.cu`。运行按实际读取地址发出请求。

每阶段每个命中页首次读取时发出一个 4 KiB 请求。等待中的页由 GPU 发布到有界 FIFO，主机用 EventLab 接受最多 16 页的可用批次。两个阶段更新同一个介质实例，GPU 页就绪表在阶段间清空。后端成功和对应截止时间成立后，原生 load 以完成回执里的 GPU 页地址为输入。词嵌入按真实 token ID 取行，只有触达的页发出读取请求。

完整输出投影在两个阶段分别计算末位置的 151,936 个输出。两组对连续 F16→F32 转换和单列 F16 矩阵向量乘法使用至多 512 KiB 源数据的启动分块。完整输出投影每次最多 256 行，每阶段实际启动 594 次。各块沿用原生核、绝对输入输出位置、算术和 CUDA stream。比较同构建关闭计时的原生对照、开启计时的运行和封存的未切分原生参考。

每个 GPU 读取都更新对应页的最早与最晚放行时间、读取和字节数、动态指令位置及 2 B 覆盖位图。FFN 归一化与词嵌入额外保留被触达页的逐元素重复次数。验收核对页回执、放行下界、访问覆盖、重复次数、两个阶段五类输出、两份完整 logits、KV 与序列释放。以每页界值和重复计数留证，覆盖和早读判定可复核。

通过 `build.ps1` 构建 Windows CUDA 13 候选，提交代码，用 `run.py receipt` 封存身份。用统一登记流程直接运行 `run.py measure`，传入冻结参考 manifest、模型和候选身份，并显式传入 `{config}`、`{run_dir}` 和 `{resource_root}`。
